# 문제 정의 (Problem)

## 한 문장 요약

> 시외버스 시간표의 소요시간은 **고정값**이지만, 실제 이동시간은 **날짜·요일·시간대·교통 상황**에 따라 달라진다.
> 사용자가 정말 알고 싶은 것은 "시간표에 몇 분이라고 적혀 있나"가 아니라 **"지금 이 버스를 타면 실제로 몇 시쯤 도착하나"** 이다.

## 상황 예시

```
청주 → 서울 · 금요일 17:00 출발
시간표 소요시간  1시간 40분  → 시간표상 도착 18:40
실제로는?        금요일 저녁 정체로 더 걸릴 가능성이 높다
```

- 18:40 도착을 믿고 19:00 약속을 잡았다가 늦는 경험
- 반대로 심야 버스는 시간표보다 일찍 도착해 마중 나올 사람과 시간이 어긋나는 경험
- "몇 시 버스를 타야 19시까지 도착할까?"를 감(感)으로 판단해야 하는 상황

## 누가 겪는가

| 사용자 | 상황 |
|---|---|
| 주말마다 귀가/귀경하는 대학생·직장인 | 금요일 저녁 출발, 일요일 오후 복귀 — 정체가 가장 심한 시간대에 가장 자주 탄다 |
| 약속·면접·환승이 있는 사람 | 도착시각이 중요한데 시간표 숫자만으로는 여유를 판단하기 어렵다 |
| 마중 나가는 가족 | 버스가 실제로 언제쯤 도착할지 알고 싶다 |

## 기존 서비스와의 차이

| 구분 | 버스 예매/시간표 서비스 | 지도 앱 길찾기 | **BUSTA** |
|---|---|---|---|
| 기준 | 운수사 고정 소요시간 | 승용차/대중교통 **현재 시점** 경로 | 시외버스 **특정 출발편** |
| 미래 날짜·요일 반영 | ✗ | 일부(승용차 미래 길찾기) | ✓ (핵심 기능) |
| 시간표 대비 차이 표시 | ✗ | ✗ | ✓ "시간표 대비 +28분" |
| 출발편 간 비교 | 시간표 나열 | ✗ | ✓ 시간대별 예상 소요 |
| 데이터 신뢰도 표시 | - | - | ✓ Mock/실데이터 명시 |

지도 앱은 "지금 차로 가면"에 강하고, 예매 서비스는 "좌석과 시간표"에 강하다.
**"그 버스를 그날 그 시간에 타면"** 이라는 질문에 직접 답하는 곳이 비어 있다.

## 기능 요구사항 (자연어)

1. 사용자는 출발지·도착지·날짜·출발시간을 선택할 수 있어야 한다.
2. 시스템은 해당 출발편의 **시간표 소요시간, 예상 실제 소요시간, 예상 도착시간, 시간표 대비 차이**를 보여줘야 한다.
3. 시스템은 결과가 **어떤 데이터로 계산되었는지(데이터 상태)** 를 항상 보여줘야 한다. 실제 데이터가 아니면 반드시 경고한다.
4. 시스템은 같은 날 **시간대별 예상 소요시간**을 그래프로 보여줘야 한다.
5. 시스템은 선택한 편의 **앞뒤 출발편과 비교**할 수 있게 해야 한다. 단, 근거가 부족한 단계에서는 "최적/가장 빠름"이라고 단정하지 않는다.
6. (향후) 사용자가 **목표 도착시각**을 입력하면 가능한 출발편들을 비교해 보여줘야 한다.

## 비기능 요구사항

- **정직성**: 근거 없는 정확도·확률을 표시하지 않는다. Mock 데이터는 Mock이라고 쓴다.
- **3초 이해**: 결과 화면에서 가장 큰 정보는 예상 도착시각이다.
- **교체 가능성**: 데이터 소스와 예측 방식은 UI를 고치지 않고 교체할 수 있어야 한다.
- **재현성**: 같은 입력은 같은 결과를 낸다 (랜덤 금지). 테스트와 발표 시연이 가능해야 한다.

## 성공 기준

| 단계 | 기준 |
|---|---|
| MVP (현재) | 검색 → 결과 → 시간대별 분석 플로우가 실제로 동작하고, 데이터 상태가 명확히 표시된다 |
| Phase 3 | 실제 시간표(TAGO)와 도로 예측 데이터 한 가지 이상이 연결된다 |
| Phase 4 | 실제 운행 기록과 예측값의 오차(MAE)를 측정해 공개할 수 있다 — **이때 처음으로 "정확도"를 말한다** |
