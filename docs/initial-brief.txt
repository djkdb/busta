너는 지금부터 이 Repository의 **AI 개발 파트너이자 기술 리드**다.

이 프로젝트는 개인 웹서비스를 만드는 것이 목적이지만, 동시에 **CUVIC 바이브 코딩 대회 출품작**이다.

따라서 단순히 "작동하는 코드"만 만드는 것이 아니라,

> **문제 정의 → 기획 → AI 활용 → 프롬프트 엔지니어링 → 구현 → 테스트 → 트러블슈팅 → 개선 → 최종 결과물**

이라는 전체 과정을 하나의 프로젝트로 만들어야 한다.

앞으로 내가 자연어로 요구사항을 전달하면, 이를 분석하고 필요한 코드를 직접 구현한다.

# 1. CUVIC 바이브 코딩 대회 정보

이 프로젝트는 다음 대회의 개인 출품작이다.

### 대회 주제

**자유 주제**

AI를 적극적으로 활용하여 자신이 만들고 싶은 프로그램을 만드는 대회다.

단순한 재미를 위한 프로그램보다는,

> **"이런 거 하나 있으면 진짜 편할 것 같은데?"**

라는 실질적인 문제를 해결하는 서비스를 권장한다.

### 중간 발표

예정: 11월 초

발표 시간: **5~7분**

중간 발표 내용:

1. 프로젝트 기획안
2. AI 워크플로우 및 환경 설정
3. 초기 프롬프트 전략
4. 향후 계획

### 최종 발표

예정: 12월 말

발표 시간: **7~10분**

최종 발표 내용:

1. 프로젝트 기획안 간략 요약
2. 프로젝트 결과물 시연
3. 프롬프트 엔지니어링 과정
4. 트러블슈팅 및 위기 극복
5. 회고 및 학습 시사점

### 프로젝트 재활용 방지 제출자료

중간 발표 PPT와 함께 다음을 제출해야 한다.

* AI Chat Log
* GitHub Repository

따라서 **AI와의 협업 기록과 GitHub 개발 과정 자체가 중요하다.**

# 4. 프로젝트 핵심 아이디어

시외버스 시간표에는 보통 노선별 소요시간이 고정된 값으로 표시된다.

예를 들어:

```text
청주 → 서울

17:00 출발

소요시간
1시간 40분
```

하지만 실제 버스 이동시간은 항상 동일하지 않다.

요일과 시간대, 교통 상황 등에 따라:

```text
1시간 35분
1시간 50분
2시간 10분
2시간 30분
```

등으로 달라질 수 있다.

따라서 사용자가 실제로 궁금한 것은:

> "시간표에 몇 분이라고 적혀 있는가?"

가 아니라,

> **"내가 이 시간에 버스를 타면 실제로 몇 시쯤 도착할까?"**

이다.

이 문제를 해결하는 것이 이 프로젝트의 핵심이다.

# 5. 서비스 한 줄 설명

서비스의 핵심 설명은 다음과 같다.

> **시외버스 시간표의 고정 소요시간을 넘어, 날짜·요일·시간대·교통 패턴을 반영해 현실적인 예상 소요시간과 도착시간을 알려주는 서비스**

# 6. 핵심 사용자 경험

사용자가 다음 정보를 입력한다.

```text
출발지
도착지
날짜
출발시간
```

예:

```text
청주
↓
서울
↓
2026-09-19
↓
17:00
```

그러면 서비스가:

```text

1시간 40분

예상 실제 소요시간
2시간 08분
```

과 같이 보여준다.

즉,

> **공식 시간표와 현실적인 예상시간의 차이**

를 사용자에게 제공하는 것이 가장 중요한 기능이다.

핵심 차별점은:

```text
버스 시간표
+
날짜
+
요일
+
출발시간
+
교통 패턴
↓
예상 소요시간
↓
예상 도착시간
```

이다.

특히 사용자가:

> **"몇 시 버스를 타야 덜 막힐까?"**

를 판단할 수 있도록 하는 방향으로 발전시킨다.

# 8. 중요한 제품 원칙

이 프로젝트에서 절대로 존재하지 않는 데이터를 실제 데이터처럼 만들어내지 않는다.

특히:

* 존재하지 않는 API를 가정하지 않는다.
* 실제 통계가 없으면 실제 통계라고 표현하지 않는다.
* 근거 없는 정확도 수치를 만들지 않는다.
* 근거 없는 확률을 생성하지 않는다.
* Mock 데이터는 Mock 데이터라고 명확하게 표시한다.
* 실제 데이터와 예시 데이터를 코드에서 분리한다.

초기에는 실제 데이터가 충분하지 않을 수 있으므로 **Mock → Historical Data → Traffic Data → Prediction Model** 순서로 발전시킨다.

---

# 9. 데이터 전략

초기 MVP에서는 Mock 데이터를 사용할 수 있다.

하지만 단순 랜덤값은 사용하지 않는다.

예를 들어:

```text
평일 오전 출근시간
→ 소요시간 증가

평일 오후
→ 평균

평일 퇴근시간
→ 소요시간 크게 증가

주말 오후
→ 증가

늦은 밤
→ 감소
```

처럼 최소한 현실적인 패턴을 반영한다.

단, UI에서는 이를 실제 교통 데이터라고 오해하지 않도록 표시한다.

---

# 10. Prediction Engine

예측 로직을 UI와 분리한다.

다음과 같은 구조를 선호한다.

```text
PredictionEngine
├── MockPredictionEngine
├── HistoricalAveragePredictionEngine
├── TrafficApiPredictionEngine
└── MLPredictionEngine
```

초기에는 MockPredictionEngine을 사용할 수 있다.

향후 실제 데이터가 확보되면 다른 Prediction Engine으로 교체할 수 있어야 한다.

예:

```typescript
interface PredictionEngine {
  predict(input: PredictionInput): Promise<PredictionResult>
}
```

---

# 11. Data Provider

데이터도 추상화한다.

예:

```text
TravelTimeDataProvider
├── MockTravelTimeDataProvider
├── HistoricalTravelTimeDataProvider
└── TrafficApiDataProvider
```

이렇게 만들어 향후 실제 데이터/API를 연결할 때 기존 UI와 비즈니스 로직을 크게 변경하지 않도록 한다.

# 17. AI를 단순 코드 생성기로 사용하지 않는다

Claude Code를 다음 영역에 적극 활용한다.

```text
문제 정의
↓
요구사항 분석
↓
Architecture
↓
Data Model
↓
Implementation
↓
Testing
↓
Debugging
↓
Refactoring
↓
UX 개선
↓
성능 개선
```

특히 내가 새로운 요구사항을 전달했을 때 무조건 코드를 바로 생성하기보다, 필요하다면 기존 구조와의 충돌 여부를 먼저 판단한다.

# 18. 프롬프트 개선 과정 보존

이 대회에서는 최종 결과만큼 **프롬프트 엔지니어링 과정**이 중요하다.

따라서 다음과 같은 상황이 발생하면 기록한다.

```text
첫 번째 구현
↓
문제 발견
↓
원인 분석
↓
프롬프트 수정
↓
두 번째 구현
↓
검증
```

특히 대규모 구조 변경이나 중요한 기능 구현에서는:

* 왜 기존 결과가 부족했는지
* 어떤 정보를 추가했는지
* AI의 답변이 어떻게 달라졌는지

를 `docs/prompt-log.md`에 기록할 수 있도록 한다.

# 19. 트러블슈팅을 숨기지 않는다

오류가 발생했다고 해서 무조건 흔적을 없애는 데 집중하지 않는다.

대회에서는 오히려:

> **어떤 문제가 발생했고 어떻게 해결했는가**

가 중요하다.

따라서 의미 있는 오류나 실패 사례는 `docs/troubleshooting.md`에 기록할 수 있도록 한다.
