# Roadmap

> 기능 수가 아니라 **데이터 신뢰도**가 올라가는 순서로 발전합니다.

```
Mock Data ──▶ Real Timetable ──▶ Traffic Data ──▶ Historical Data ──▶ Prediction Model
 (현재)        Phase 3            Phase 3          Phase 4            Phase 5 (데이터 충분 시)
```

## ✅ Phase 1 — 핵심 MVP (완료)
- 출발지 → 도착지 → 날짜 → 출발시간 → ETA
- 시간표 소요시간 / 예상 실제 소요시간 / 예상 도착 / 시간표 대비 차이
- 데이터 상태 표시 (🟡 시연용 예측 데이터)
- 예측 근거(적용된 가정 규칙) 표시

## ✅ Phase 2 — 분석 (완료)
- 시간대별 예상 소요시간 차트 (시간표 기준선 대비)
- 앞뒤 출발편 비교 ("최적" 표현 없이)

## 🔶 Phase 3 — 실제 데이터 연결 (진행 중)
1. ✅ **TAGO 고속/시외버스정보 → `TagoScheduleDataProvider`** (실제 응답 확인 후 구현, 노선 9개)
   - 남은 과제: API가 어제~모레만 제공 → **매일 시간표를 수집·보관**해서 먼 날짜도 "같은 요일의 최근 실제 시간표"로 보여주기
2. ✅ **특일정보 API → `KasiHolidayCalendar`**
3. ⏭ **교통 데이터 → `TrafficApiTravelTimeDataProvider`**
   - 카카오 미래 운행 정보 / TMAP 타임머신 중 무료량·약관 확인 후 선택
   - 버스 보정: 도로 예측시간 × 대형차 계수 + 휴게소 정차 + 터미널 진출입 (계수는 처음엔 가정치로 명시)
   - 노선×15분 버킷 캐싱
4. 터미널 좌표 테이블 구축

## 🔶 Phase 4 — 예측 고도화 (Historical)
0. ✅ **TAGO 고속버스도착정보 연결** — 오늘 날짜 결과 화면에 실제 운행(도착 완료·운행 중) 표시, 첫 검증 기록 (`docs/validation.md`: 가정 규칙 MAE 약 23분 vs 시간표 약 3분, n=8)
1. ⏭ **도착 기록 수집기**로 실제 운행 이력(`TravelTimeObservation`) 자체 수집 — 가능한 한 빨리 수집 시작 (데이터는 시간이 지나야 쌓임). 도착정보는 도착 후 잠깐만 남으므로 15분 이하 주기로 조회해야 한다
2. `HistoricalAverageTravelTimeDataProvider`: 노선 × 요일유형 × 시간대 버킷 중앙값/P80
3. **처음으로 정확도 측정**: Mock/Traffic/Historical 각각의 실제 대비 MAE 비교 → 그때부터 "정확도" 표기
4. 결과 화면에 표본 수(`sampleSize`)와 범위 표시

## Phase 5 — ML (조건부)
- 노선별 수백 건 이상의 관측이 쌓였을 때만 진행
- 설명변수: 요일유형, 시간대, 특일(연휴 D-1/D+1), 도로 혼잡 이력, 날씨
- Historical 평균보다 검증 오차가 낮을 때만 교체

## ✅ Phase 6 — 사용자 의사결정: 목표 도착시각 (Mock 기반 완료)
구현: `lib/prediction/planner.ts`, `/plan` 화면, 검색 폼 "도착시각으로" 모드
- 예상 기준 늦지 않는 마지막 출발편 + 여유 15분 미만이면 여유 있는 대안 제시
- **시간표 함정**: 시간표상 제시간이지만 예상으로는 늦는 출발편 경고
- 남은 과제: 실제 데이터 단계에서 "여유 15분"(UI 규칙)을 예측 오차 분포(P80 등) 기반으로 교체, 다음날 도착 목표 지원

```
"서울에 19:00까지 도착해야 함"
15:40 출발 → 17:31 예상 도착
16:40 출발 → 18:42 예상 도착
17:40 출발 → 19:56 예상 도착 ⚠️
```
- Mock 단계에서는 "추천"이 아니라 "예상 기준 비교"로만 표시, 실제 데이터 단계에서 여유시간(P80 기준) 제안
