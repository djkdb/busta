## 1. vitest 설치 실패

### Symptom
```
npm install -D vitest
npm error Cannot read properties of null (reading 'edgesOut')
```
버전을 바꿔 `vitest@4.1.4`로 재시도해도 같은 오류.

### Cause
`create-next-app`이 `@types/node@^20`을 넣었지만 실행 환경은 Node 22.
vitest 5는 `@types/node`를 `^22 || >=24` peer로 요구 → 충돌. vitest 4에서는 이 충돌이 npm arborist 내부 버그(`edgesOut`)로 가려져 원인이 보이지 않았다.

### Initial AI Diagnosis
"npm 버그일 수 있으니 버전을 바꿔 재시도" → 실패.

### Investigation
npm 디버그 로그에서 스택 직전의 `fetch manifest @vitest/browser-playwright` 확인 → peer 해석 문제로 판단 → 최신 vitest 5로 시도하자 **진짜 원인이 ERESOLVE 리포트로 드러남**.

### Solution
`--legacy-peer-deps`로 덮지 않고 `@types/node`를 런타임과 같은 22로 올림. `engines.node >=22`, `.nvmrc` 추가.

### Verification
`npm ls vitest @types/node` → `vitest@5.0.2`, `@types/node@22.x`. 테스트 실행 성공.

### Lesson
불투명한 도구 오류는 **버전을 바꿔 원인을 드러나게** 하는 것도 디버깅 방법이다. 우회 플래그는 원인을 숨긴다.

## 2. `Cannot find name 'LayoutProps'`

### Symptom
`tsc --noEmit` 실패: `app/layout.tsx: Cannot find name 'LayoutProps'`.

### Cause
Next.js 16의 `LayoutProps`/`PageProps`는 `next typegen` 또는 빌드 때 `.next/types`에 **생성되는** 전역 타입. 빌드 전에 tsc만 돌리면 없다.

### Solution
`"typecheck": "next typegen && tsc --noEmit"`.

### Lesson
프레임워크 버전이 AI 학습 시점보다 새로우면 "당연한" 가정이 틀린다. `AGENTS.md`의 지시대로 번들 문서(`node_modules/next/dist/docs`)를 먼저 확인하는 습관이 필요했다.

## 3. 결과 화면(+45분)과 차트 강조값(+41분) 불일치 ⭐ 발표 추천

### Symptom
서울(경부)→청주, 금요일 **17:20** 출발 검색.
- 상단 ETA: 예상 2시간 25분, **시간표 대비 +45분**
- 바로 아래 시간대별 차트: 17시 막대가 강조되어 있고 판독값은 **17:00 출발, +41분**

같은 버스에 대해 화면에 두 개의 다른 숫자가 보임.

### Cause
시간대별 분석을 "정각 출발 기준"으로 만들고, 선택 출발편은 "같은 시(hour)의 막대"로 강조했다. 계산은 둘 다 맞지만 **서로 다른 출발시각의 값**이었다.

### Initial AI Diagnosis
유닛 테스트 46개가 모두 통과 → AI는 기능이 완료됐다고 판단한 상태였다. 테스트는 각 함수가 맞는지만 봤고, **화면에서 두 값이 나란히 놓였을 때의 의미**는 검증하지 않았다.

### Investigation
AI가 Playwright로 실제 사용자 플로우를 클릭하고 모바일 스크린샷을 판독하는 단계에서 발견.

### Solution
시간대별 시리즈를 선택 출발편의 "분"을 유지해 생성 (17:20 선택 → 06:20, 07:20 … 23:20).
강조 막대 = 선택 출발편 그 자체가 되어 숫자가 항상 일치. 차트 부제도 "1시간 간격 출발 가정"으로 수정.

### Verification
회귀 테스트 추가: `hourly profile ↔ ETA consistency` — 17:20 결과와 차트의 17:20 포인트가 같은 소요시간·도착시각인지 확인. 브라우저 재검증에서 판독값 `17:20 출발 · +45분` 확인.

### Lesson
**"테스트 통과"와 "사용자가 이해 가능"은 다르다.** 숫자를 보여주는 서비스에서는 한 화면 안의 숫자끼리 일관성이 곧 신뢰다. UI 검증을 AI의 시각적 확인 루프에 포함시킨 것이 효과가 있었다.

## 4. 차트 라벨 겹침 / 잘림

### Symptom
X축 "17시"(선택 강조)와 "18시"(3시간 간격 눈금)가 붙어 `17시8시`로 보임. Y축 기준선 라벨 "시간표"가 왼쪽에서 잘림.

### Cause
강조 라벨과 주기 라벨의 충돌을 고려하지 않음. 한글 라벨 폭을 영문 기준으로 여백을 잡음.

### Solution
선택 라벨의 ±1칸 이웃 눈금은 생략. 왼쪽 여백 34 → 40px.

### Verification
라이트/다크 모바일(390px) 스크린샷 재확인.

### Lesson
차트는 "렌더링되면 끝"이 아니라 **실제로 보고** 확인해야 한다.

## 5. 차트 축 설계: 과장 vs 가독성

### 문제
소요시간 자체(100분 vs 128분)를 막대로 그리면:
- 0에서 시작하면 차이가 작아 보여 "이 시간대는 오래 걸린다"가 잘 안 보임
- 축을 90분부터 시작하면 차이가 과장됨 (막대 차트에서 잘린 축은 대표적인 왜곡)

### 결정
**시간표 소요시간을 0 기준선**으로 두고 막대 = 시간표 대비 추가/단축 시간(분). 기준선이 진짜 0이라 왜곡이 없고, 메시지("평소보다 오래 걸린다")가 막대 방향으로 바로 보인다. 절대값은 판독 영역과 "표로 보기"에서 제공.

## 6. 공식 데이터 사이트 접근 차단

### Symptom
데이터 조사 서브에이전트가 data.go.kr, data.ex.co.kr, its.go.kr, 카카오/SK 개발자 사이트 등 **공식 문서를 한 건도 직접 열지 못함** (개발 컨테이너 네트워크 정책).

### Risk
AI가 검색 요약이나 기억으로 엔드포인트·필드·요금을 "확인된 것처럼" 쓰는 것 — 프로젝트 철학("존재하지 않는 API를 가정하지 않는다") 위반.

### Solution
- 근거를 `[검색확인] / [코드확인] / 미확인` 3등급으로 분리 표기
- 공식 문서 대신 실제 호출 코드(GitHub 공개 라이브러리 소스)를 열어 엔드포인트·필드명 교차 확인
- "구현 전 확인 체크리스트" 작성 → 사람이 직접 확인할 항목을 명확히

### Lesson
AI 조사 결과는 **내용보다 근거 수준이 먼저**다. 프롬프트에 "확인 못 하면 미확인이라고 써라"를 넣은 것이 결정적이었다.

## 7. 타임존 요일 버그 (예방)

### 위험
`new Date("2026-10-02").getDay()`는 UTC 자정으로 해석되어 UTC-x 환경에서는 목요일(4)이 나온다. 서버(UTC)와 브라우저(KST)에서 요일·"오늘"이 달라질 수 있다.

### Solution
날짜는 문자열, 시각은 분 정수로만 다루고 UTC 달력 연산으로 요일 계산. "오늘"은 UTC+9 오프셋으로 계산.

### Verification
같은 테스트를 `TZ=UTC`, `Asia/Seoul`, `America/Los_Angeles`, `Pacific/Kiritimati(UTC+14)`에서 실행 → 전부 통과. 자정 넘김(23:00+100분 → 다음날 00:40), 연말(12/31 → 1/1), 윤년 테스트 포함.

## 8. "공식 소요시간" 용어 충돌

### Symptom
요구사항은 결과 화면에 "공식 소요시간"을 표시하라고 했지만, 현재 시간표는 사람이 만든 **예시 데이터**.

### Solution
UI 표기를 **"시간표 소요시간"** 으로 하고, 데이터 상태 영역에 "예시 시간표: 실제 운수사 시간표와 다를 수 있음"을 명시. TAGO 연동(Phase 3) 후 출처가 실제 데이터가 되면 "공식"이라는 표현을 검토.

### Lesson
요구사항의 단어 하나도 데이터 출처와 맞는지 확인해야 한다. → `prompt-log.md` V2 개선점으로 반영.

## 9. E2E 오탐: "17:20"을 눌렀는데 15:20 결과로 이동

### Symptom
목표 도착시각 화면(서울→청주, 금 19:00까지)에서 Playwright로 `a:has-text("17:20")`를 클릭하자 `/result?...time=15:20`으로 이동했다. 처음에는 링크가 잘못 연결된 버그처럼 보였다.

### Cause
15:20 출발편의 **예상 도착시각이 정확히 17:20**이었다. `has-text("17:20")`가 목록 위쪽에 있는 15:20 행(도착시각 텍스트)을 먼저 찾았다. 앱은 정상이고 **테스트 셀렉터가 모호**했다.

### Initial AI Diagnosis
"링크 buildHref가 잘못됐을 수 있다" → 코드를 고치기 전에 스크린샷부터 확인.

### Investigation
스크린샷에서 15:20 행의 오른쪽에 "예상 도착 17:20"이 표시된 것을 확인 → 셀렉터 문제로 판정.

### Solution
출발시각 칸(`span.font-bold`)의 텍스트가 정확히 `17:20`인 행만 찾도록 셀렉터를 좁혔다. 앱 코드는 수정하지 않았다.

### Verification
재실행 결과 `/result?...time=17:20`으로 이동.

### Lesson
시간을 다루는 서비스에서는 **출발시각과 도착시각이 같은 형식(HH:MM)** 이라 텍스트 기반 테스트가 쉽게 오탐을 낸다.
"테스트가 실패했다 = 앱이 틀렸다"로 바로 가지 않고, 실패 화면을 먼저 보는 습관이 불필요한 코드 수정을 막았다.

## 10. AI가 만든 공휴일 목록에 노동절·제헌절 누락 ⭐ 발표 추천

### Symptom
Mock 예측의 요일 분류에 쓰는 2026 공휴일 목록(`data/calendar/holidays-kr.ts`)을 처음에 AI가 작성했다. 특일정보 API를 연결하면서 두 목록을 자동 대조하자 **API에만 있는 날짜 2개**가 나왔다: `2026-05-01 노동절`, `2026-07-17 제헌절`.

### Cause
두 날 모두 최근 법 개정으로 공휴일이 된 날이라 AI의 학습 지식에 반영돼 있지 않았다. 처음 작성할 때부터 "제헌절 재지정 여부 불확실"이라고 스스로 의심했던 부분이다.

### Why it didn't cause damage
처음부터 파일에 "⚠️ API로 검증 필요"를 명시했고, 실제 데이터가 연결되자마자 **대조 스크립트로 차이를 기계적으로 찾았다.**

### Solution
- 정적 목록 수정 (키가 없을 때의 fallback)
- 키가 있으면 `KasiHolidayCalendar`(특일정보 API)를 기본으로 사용
- API 조회에 실패하면 정적 목록으로 **조용히 대체하지 않고** "공휴일 정보 없이 요일 기준으로 계산"했다고 화면에 안내

### Lesson
**AI가 만든 "사실 데이터"는 코드보다 더 검증이 필요하다.** 코드는 테스트가 잡아주지만, 날짜 목록 같은 데이터는 틀려도 아무 오류가 나지 않는다. 불확실한 데이터는 처음부터 출처와 검증 계획을 함께 적어두자.

## 11. curl은 되는데 Next 서버에서는 HTTP 403

### Symptom
같은 키로 터미널에서 `curl` 호출은 성공했지만, Next 서버의 `/api/timetable`은 모든 노선에서 "시간표 정보를 불러오지 못했습니다". 서버 로그: `JSON 이 아닌 응답 (HTTP 403)`.

### Cause
개발 컨테이너는 외부 통신을 프록시(`HTTPS_PROXY`)로 보낸다. `curl`은 이 변수를 읽지만 **Node 내장 `fetch`는 기본적으로 읽지 않아** 프록시를 우회했다가 차단됐다.

### Investigation
키 문제라면 curl도 실패해야 한다 → 클라이언트별 차이로 범위를 좁힘 → 환경 문서에서 "Node 내장 fetch는 `NODE_USE_ENV_PROXY=1` 필요(Node ≥ 22.21)" 확인.

### Solution
개발 환경에서만 `NODE_USE_ENV_PROXY=1`로 서버 실행. **코드는 바꾸지 않았다** — 일반 배포 환경(Vercel 등)에서는 필요 없는 설정이기 때문.

### What went right
에러 메시지 설계가 진단을 도왔다: 클라이언트가 "인증 오류(키 문제)"와 "HTTP 403 비JSON(중간 차단)"을 구분해서 로그에 남겼고, 키는 로그에 전혀 노출되지 않았다.

## 12. 조사 문서의 추정 ≠ 실제 API 응답

### Symptom
검색으로 작성한 `data-sources.md`의 추정과 실제 응답이 여러 곳에서 달랐다 (전체 표: `data-sources.md` §6).
- 고속은 12자리, 시외는 **14자리** 시각
- 자정 출발편이 **"24:00"** 으로 옴 → Python `strptime`이 `unconverted data remains: 0`으로 실패하면서 발견
- 시외버스는 "당일만"이라더니 **내일도 조회됨**, 고속은 **어제~모레**만 조회됨
- 고속 터미널 목록에 `cityName` 없음

### Decision
키를 받기 전 "추정으로 파서를 먼저 만들자"는 선택지가 있었지만, **실제 응답을 먼저 받고 구현**하기로 했다 (프로젝트 원칙: 존재하지 않는 API를 가정하지 않는다). 추정대로 만들었다면 24:00 편과 14자리 시각에서 모두 깨졌을 것이다.

### Solution
- 실제 응답을 fixture로 저장하고, 발견된 특이점마다 테스트를 하나씩 고정
- 24:00 → 다음날 00:00으로 정규화하고, 날짜 D 시간표 = D 목록 + (D-1 목록 중 실제 출발일이 D인 편)
- 공개 전 날짜는 가까운 날의 시간표를 **"참고 시간표"라고 명시**해서 보여줌

### Lesson
AI 조사는 "어디를 봐야 하는지"를 알려주는 데 유용했지만, **형식의 세부사항은 실제 응답만이 정답**이다.

## 13. 실제 API 첫 조회 35초

### Symptom
캐시가 없는 날짜의 결과 페이지가 35초 걸림 (캐시 후 0.02초).

### Cause
개발 환경 프록시 터널이 가끔 중간에 끊기는데(`ws_closed_mid_exchange`), 끊긴 요청이 **타임아웃 10초**까지 멈춰 있다가 재시도. 10초 × 여러 번 + 백오프 ≈ 35초.

### Solution
정상 응답은 1초 안팎이므로 1회 타임아웃을 4초로 줄이고 재시도를 3회로. 끊긴 연결을 빨리 포기하고 다시 시도한다.

### Verification
같은 조건 첫 조회 35초 → **4.6초**. 조회 결과는 노선·날짜별로 30분 캐시.

### Lesson
재시도 설계에서는 "몇 번"보다 **"한 번에 얼마나 기다리나"** 가 체감 속도를 좌우한다.

## 14. BUSTA 가정 규칙이 시간표보다 크게 틀렸다 ⭐ 발표 추천

### Symptom
TAGO 고속버스도착정보로 오늘(9/26, 추석 연휴 토요일) 실제 도착한 8편을 모았더니, 시간표(90분) 평균 오차는 약 3분, **BUSTA 가정 규칙은 약 23분**이었다. 청주→서울은 실제 84~89분인데 BUSTA는 124분으로 예측했다.

### Cause
공휴일이면 "귀경 정체 +28%"를 적용하는 규칙이 추석 다음날 토요일 오후에는 맞지 않았다. 가정 규칙이 실제 교통을 대신할 수 없다는 것을 실측이 보여줬다.

### Decision
- 8건으로 규칙을 고치면 과적합이다 → **수치는 그대로 두고** 실제 운행 기록을 결과 화면에 나란히 보여준다
- 실제 도착 기록 수집을 시작해 표본을 쌓은 뒤 규칙을 실측 비율로 교체
- 전체 표: `docs/validation.md`

### Lesson
Mock 단계부터 "🟡 가정 규칙"이라고 표시해 둔 덕분에, 틀린 것이 드러나도 사용자를 속인 것이 아니다. **검증할 수 있는 구조를 먼저 만들고, 틀린 것을 발견하는 것 자체가 진전이다.**

## 15. "실시간 도착정보"가 실시간이 아니었다

### Symptom
17:19에 조회한 도착정보에서 운행 중인 모든 버스의 "도착 예정 − 남은 시간"이 16:44로 같았다. 4분 간격으로 다시 조회해도 기준 시각이 16:59에서 바뀌지 않았다.

### Cause
원본 데이터가 **약 15분 주기로 갱신되고, 조회 시점보다 20~35분 늦다.** 또 아직 출발하지 않은 편들은 서로 다른 출발시각인데 같은 도착 예정시각(18:02)을 갖는 등 의미 없는 값이었다.

### Solution
- 기준 시각 = 운행 중 편들의 "도착 예정 − 남은 시간" 최빈값 → 화면에 "16:59 기준 (실시간 아님)" 표시
- 기준 시각 이후 출발 편(출발 전)은 도착 예정을 표시하지 않음
- 경로도 조사 문서의 `ExpBusArrInfoService`가 아니라 `ExpBusArrInfo`(신경로)만 동작, 오류는 `response` 래퍼 없이 최상위 `header`로 오는 형식도 있었다 → 클라이언트에서 처리

### Lesson
API 이름에 "실시간"이 있어도 **데이터의 기준 시각을 데이터로부터 직접 확인**해야 한다.
