## Prompt V1 — 마스터 프롬프트 ("BUSTA 프로젝트 전체 고도화 및 구현 시작")

### Goal
빈 Repository에서 시작해, 대회 심사 기준을 만족하는 실행 가능한 MVP와 개발 과정 문서를 한 번에 만든다.

### Prompt (요약 — 원문은 약 36개 섹션)
- 역할 부여: "AI 개발 파트너이자 기술 리드"
- 맥락: CUVIC 대회 일정, 중간/최종 발표 항목, **심사 기준과 배점**
- 문제 정의와 핵심 UX 예시 (`청주→서울 17:00 / 공식 1h40m / 예상 2h08m / 도착 19:08`)
- **제품 철학 (금지 사항)**: 가상의 정확도 금지, Mock은 Mock이라고 표시, 존재하지 않는 API 가정 금지
- 아키텍처 요구: `PredictionEngine`, `TravelTimeDataProvider` 인터페이스 분리, 도메인 모델 초안
- 개발 순서 STEP 1~14, Phase 1~6, 커밋 메시지 규칙, 보고 형식
- "계획만 쓰고 끝내지 말 것", "불확실한 부분은 인터페이스까지만"

### AI Result
- Repository 분석 → 빈 저장소 확인 → Next.js 16 + TS + Tailwind + Vitest 스캐폴딩
- 도메인 모델, 타임존 안전 시간 유틸, Provider/Engine 계층, Mock 규칙 엔진, 검색·결과·차트·비교 UI
- 테스트 47개, 문서 7종, 기능 단위 커밋
- 데이터 조사는 서브에이전트로 병렬 수행

### Problem (프롬프트 관점에서 발견한 점)
1. **예시 숫자가 목표처럼 읽힐 위험**: 프롬프트의 `2h08m / 19:08` 예시를 그대로 맞추도록 Mock 수치를 조정하면 "그럴듯한 숫자 만들기"가 된다. AI는 예시를 맞추지 않고 규칙에서 나온 값(금요일 17:00 → 2h05m, 19:05)을 그대로 두었다.
2. **"공식 소요시간"이라는 용어 충돌**: 프롬프트는 결과 화면에 "공식 소요시간"을 표시하라고 했지만, 현재 시간표는 공식 데이터가 아닌 예시다. 그대로 쓰면 제품 철학(Mock은 Mock이라고)과 충돌 → UI에서는 **"시간표 소요시간"** 으로 표기하고 데이터 상태에 "예시 시간표"를 명시했다.
3. **"시간대별 분석"의 기준 시각이 모호**: 정각 기준으로 만들었더니 17:20 출발 결과(+45분)와 차트 강조 막대(17:00, +41분)가 달라 보였다 (`troubleshooting.md` #3).
4. **범위가 넓어 한 번에 모든 STEP을 수행** → 각 STEP의 검증 깊이가 얕아질 위험. 브라우저 검증 단계를 별도로 둬서 보완.

### Human Feedback
✍️ 직접 기입 (V1 결과를 보고 느낀 점, 수정 요청 사항)

### Prompt V2 (제안)
다음 요청부터는 아래처럼 범위를 좁히고 검증 기준을 명시하는 것을 권장:

```
[목표] Phase 3 — 실제 시간표 연결 (TAGO 고속버스정보)
[제약] 네트워크에서 data.go.kr 접근이 막혀 있으면 실제 호출은 하지 말고,
       응답 스키마(코드확인 수준)에 맞춘 Provider + 파서 + 고정 fixture 테스트까지만 구현
[완료 기준]

 - fixture 기반 파서 테스트 통과

```

### Improvement
- 한 프롬프트에 한 Phase / 명확한 완료 기준 / 금지사항을 담는다
- 예시 수치는 "형식 예시"라고 명시해 AI가 값을 맞추려 하지 않게 한다
- 용어(공식/시간표/예상)를 데이터 상태와 연결해 정의한다

### Result
✍️ V2 적용 후 기록

## Prompt — 데이터 소스 조사 서브에이전트 (AI → AI)

### Goal
메인 구현과 병렬로, 시외버스 실제 소요시간을 만들 수 있는 데이터 소스를 조사한다.

### Prompt (요약)
- 후보 8종(TAGO 고속/시외, 도로공사, ITS, TMAP/카카오 미래 길찾기, 예매 사이트, DTG, 특일정보, 실제 도착 실적) + "추가로 찾은 것"
- 각 소스마다 동일 질문: 어떤 데이터 / 어디서 / 무료 / API / 조건 / **실제 운행 vs 도로 통행 vs 계획 시간표** / 노선 변환 / 활용 Phase
- **"API·엔드포인트·약관을 지어내지 말 것. 확인 못 하면 '미확인 (확인 필요)'"**
- 결과: 요약표 + 소스별 상세 + 단계별 전략

### AI Result
- 14개 소스 조사, 요약표와 단계별 확보 전략
- 핵심 발견: **공개된 실제 도착 실적 데이터는 없음** → TAGO 고속버스도착정보를 폴링해 자체 이력을 쌓는 전략

### Problem
- 조사 환경의 네트워크 정책이 공식 사이트(data.go.kr 등)를 차단 → 원문 확인 불가

### Improvement (AI가 스스로 적용)
- 근거를 `[검색확인] / [코드확인] / 미확인` 3등급으로 나눠 표기
- 공식 문서 대신 실제 호출 코드(GitHub 제3자 라이브러리)를 열어 엔드포인트·필드명 교차 확인
- "구현 전 확인 체크리스트"를 별도로 작성

### Result
`docs/data-sources.md`에 반영. "미확인" 항목은 Phase 3 착수 전 사람이 직접 확인해야 함.

## Prompt V2 — "목표 도착시각 역산 기능(Phase 6) 구현해줘"

### Goal
V1에서 로드맵으로 남겨둔 Phase 6(목표 도착시각 → 출발편 비교)를 구현한다.

### Prompt
```
목표 도착시각 역산 기능(Phase 6) 구현해줘
```

### AI Result
- 짧은 한 줄 프롬프트였지만, V1의 제품 철학과 `docs/roadmap.md`가 **맥락으로 남아 있어서** AI가 설계 조건을 스스로 복원했다
  - "근거가 부족하면 '최적'이라 단정하지 않는다" → 화면 문구를 "추천"이 아니라 **"예상 기준, 늦지 않는 마지막 출발편"** 으로 정함
  - "Mock은 Mock이라고" → 계획 화면에도 데이터 상태 경고를 넣고 "특정 출발편을 추천하는 것이 아닙니다"를 명시
- AI가 추가로 제안한 차별 요소: **시간표 함정(timetable trap)**. 시간표상으로는 제시간이지만 예상으로는 늦는 출발편을 따로 경고한다
- 로직(`planner.ts`)을 순수 함수로 먼저 만들고 테스트 18개를 붙인 뒤 UI를 구현했다

### Problem
- 프롬프트에 없어서 AI가 **스스로 정한 값**이 생겼다: "여유 적음" 기준 15분. 이 값은 통계가 아니라 UI 규칙이다
  → 코드 주석과 architecture 문서에 "UI 규칙"이라고 명시했고, 실제 데이터 단계에서 예측 오차 분포(P80)로 바꾸도록 로드맵에 넣었다
- 목표가 다음날인 경우(예: "01:00까지")는 이번 범위에서 지원하지 않는다

### Human Feedback
✍️ 직접 기입

### Improvement (다음 프롬프트에 반영할 점)
- AI가 임의로 정할 수 있는 **임계값**(여유 기준 등)은 프롬프트에서 미리 정하거나 "임계값은 UI 규칙으로 명시하라"고 요구한다
- 짧은 프롬프트가 잘 동작한 이유는 **문서화된 맥락**(README, roadmap, CLAUDE.md 규칙) 덕분이었다. 문서가 곧 프롬프트의 일부다

### Result
`/plan` 화면, 검색 폼 "도착시각으로" 모드, 테스트 65개 통과, 브라우저 검증 완료.
